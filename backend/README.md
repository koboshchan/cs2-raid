Trusted raid backend

Node 24 only. Run npm ci, npm test, npm run build, then npm start. All tests use fake SSG transports; no real charges or SSG calls occur. Docker build context is the repository root, using backend/Dockerfile. The multi-stage image runs tests and TypeScript compilation, prunes development dependencies and runs as node with a durable /data SQLite volume. Parent builds on its dedicated build host.

Set SSG_API_ORIGIN to the approved HTTPS SSG origin, SSG_CLIENT_ID to the public app ID and SSG_APP_SECRET to the complete confidential credential. Set a random BRIDGE_TOKEN of at least 32 characters, SERVER_ID (letters/digits/underscore/hyphen, maximum 32), DATA_DIR (default /data), CATALOG_PATH (default /app/config/prices.json) and optionally PORT (3000). Keep the app credentials exclusively on this backend. The trusted server plugin receives only BRIDGE_TOKEN. Put backend and plugin on a private compose network; never publish the backend port or expose the token to players. BRIDGE_TOKEN authenticates the trusted plugin, not individual players. The plugin must obtain SteamID64 from the authenticated engine connection and must never forward an arbitrary client-selected ID.

All routes require Authorization Bearer BRIDGE_TOKEN, reject Origin headers and disable caching. GET /health reports the closed purchase gate. GET /catalog returns the validated server catalog with integer priceCents and defaultLimitBlocked flags. POST /link and POST /link/poll take {"steamId64":"76561198000000001"}. Link creation returns four random words and verification URI, never the device token. Show words privately to that player. Pending device tokens and immutable approved Steam/app-user/grant bindings persist in SQLite. Polling claims a durable interval before the upstream call and respects Retry-After. Approval requires balance:debit. Bindings are app-local and cannot silently overwrite previous identities; unlink/relink requires operator review. Protect volume permissions and backups, since pending tokens reside there.

POST /purchase, /buy, /debit, /sell, /sellback, /cashin, /cashout, /extract, /payout and /settlement return 503 native_session_bridge_not_ready. There is no environment switch to open them, no debit worker, and no placeholder game delivery adapter wired into HTTP. Unknown routes are not handlers. Implement and independently test the native authenticated session transport before adding any money endpoint. The TypeScript adapter is a contract and mock-test aid, not a native bridge.

The dormant outbox accepts any item ID from the server-priced root JSON array of {id,entity,priceDollars,kind}. It snapshots the item and integer cents durably before networking, with stable debit/refund keys, receipt checks, SQLite FULL/WAL and CAS delivery claims. Unknown items and prices over 100000 cents fail closed. SSG currently defaults to $1000 per operation, $5000 daily and $50000 lifetime per user, with additional app-wide caps. Many raid weapons exceed the operation cap. Merely raising app configuration cannot override platform ceilings; platform/admin approval and fresh consent are required. No price is accepted from the plugin or player. Remaining live grant budgets can still reject cheaper purchases.

Lost money responses reconcile the same key. Known-no-delivery allows only a bounded refund to the original payer. Ambiguous native delivery or a crash after the delivery claim stays manual/unresolved, never automatically gives again or refunds. One unresolved purchase blocks another for the player. Operators must reconcile canonical receipts and native delivery evidence; do not reset rows or generate replacement keys.

Extraction payouts and 90% sellback are deliberately unimplemented. Refund-only cannot pay a killer from a victim's original debit or turn looted items into arbitrary issuance. Rewards require separately approved mint scope, mint budgets, replay-resistant authoritative extraction/inventory accounting and a separately reviewed implementation. Never represent a payout or sellback as a compensation refund. SSG currency is simulation currency, not real USD.

No HTTP purchase acceptance or native bridge end-to-end test is claimed. Keep the gate closed until those exist.

The offline raid-protocol module defines integer-cent cash-in snapshots up to 1500000, authenticated-session generations, extraction cash and unique gun/unused-utility inventory instances. Armor and helmets are rejected. Raid IDs accept the native 32-hex MatchId or dashed UUID and normalize to one identity. Stable operation keys bind server, raid, player and cashin/extract kind, while fingerprints detect changed amounts, sessions, intent/window and inventory. Reordered inventory is equivalent. These exports are test-only groundwork, not a journal, receipt, price calculation, mint authorization, native authentication or HTTP financial handler. No cash-in/settlement SQLite migration, network transport or worker has been added. Future journals must persist immutable snapshots before sending, reject changed fingerprints under an existing key, reconcile canonical SSG receipts after ambiguity and freeze native value through settlement. Confirm the native cash unit before integration and never substitute HUD-clamped values.

Historical permission to add configurable caps and -1 unlimited is not a saved cap or mint approval. Read-only SSG source ed6a0297e028f6c12aa0a96c74a7abc0a7db346e still rejects -1 and enforces the platform minimum ceiling. Existing linking requests debit only. Mint authorization, explicit debit/mint budgets, fresh consent, native authoritative accounting and backend receipt validation remain blockers. An SSG debit reduces the player's wallet and room issuance, not credits an app wallet. A bounded same-player refund reverses the original debit; extraction rewards would require approved mint or a separately designed conserved transfer service, neither of which is wired here.

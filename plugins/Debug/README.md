Map Debug is an independent CounterStrikeSharp plugin, built for .NET 10 against the repository's pinned CSS 1.0.379 API without NuGet packages. Install Debug.dll and Debug.deps.json together in game/csgo/addons/counterstrikesharp/plugins/Debug.

CounterStrikeSharp generates its configuration in game/csgo/addons/counterstrikesharp/configs/plugins/Debug/Debug.json, not beside the DLL. config.example.json shows the defaults. Enabled defaults to true. ReportDirectory must be absolute and defaults to /data/map-reports. The server user must be able to create and write reports.jsonl there. Mount a persistent volume at that directory. After changing configuration, reload Debug using the server console. Set Enabled to false and reload to turn off reporting and restore the economy settings.

While enabled, every server tick maintains mp_buy_anywhere at 1, mp_buytime at 1000000 minutes and mp_maxmoney at 65535, then refills human players' money to the engine's accepted mp_maxmoney value. Late map configuration execs, including the zero-money DeltaOps config, are overridden on the next tick. The most recent externally changed value of each cvar is retained as its restoration baseline. The last engine-accepted override is tracked separately so an engine clamp is not mistaken for an external configuration change. These three cvars are restored on disable, unload or map end. Existing player balances are not rolled back. No other economy cvars are changed. This is a debug-only mode and intentionally overrides the normal raid economy.

An AK's first two weapon_fire events after a reset select ladder endpoints. Only the first bullet_impact following each shot in the same server tick is accepted. Point one is saved as ladder_start; point two is saved as ladder with LadderStart carrying the first endpoint when its write was confirmed. If the first write failed or the first shot missed, point two can only save an unpaired ladder_end, and chat explicitly says point one is missing. Further AK shots are ignored until !markreset. A missed shot still consumes its ordinal. Successful marks confirm the disk write; failures never claim to have saved.

Each Glock weapon_fire allows its first same-tick impact to create a texture report. Penetration impacts after that first event are ignored. Texture is the issue category, not an assertion about the surface material. Glock reports are limited to one per player per second. A fire event from any other weapon clears that player's pending impact ticket.

!markreset is limited to once per player per second and clears your pending shot and ladder endpoints. Death, disconnect, spawn, round start and map transitions also clear marker state. !report followed by a reason records the living player's current position and eye angles. Reasons must contain 1-300 characters after trimming and cannot contain control characters. Position reports are limited to one per player every three seconds. !reports lists the latest five records; !reports N accepts 1-20 and is limited to one listing every three seconds. Listings are private command replies and show only a short report ID, UTC timestamp, issue kind, map and bounded reason text.

Reports include a random ID, UTC timestamp, map, SteamID64, bounded player name, issue category, reason, finite coordinates and angles. Ladder pairs also include the first endpoint. There is no IP address, network identifier, authentication token, environment dump or configuration path in a report or chat listing. Reasons are user-provided text, so players should not include passwords or other private information. The report volume contains player identifiers and should not be published without reviewing it.

Each accepted record is one escaped JSON line followed by FileStream.Flush(true). A success reply is sent only after the flush request succeeds. This is an OS durability request, not a guarantee against hardware or storage failure. Startup repairs an incomplete final line before appending, and loads at most the last 256 KiB for a bounded recent list. The list retains 64 records and returns at most 20. Historical reports remain in the file. Storage creation, permission or write failures disable report acceptance without intentionally stopping the server; fix the directory or disk and reload the plugin. A failed flush can leave an uncertain or partial record, so the error reply deliberately does not claim a successful save. One writer owns the file; competing plugin instances cannot open it for writing.

bullet_impact does not expose a hit entity or projectile ID. The plugin saves the first reported impact, which may be a prop or another entity; it cannot prove a world-only wall collision. Same-tick correlation deliberately rejects delayed impacts instead of attaching them to an older shot. Multiple fire events before their impacts in the same tick are intrinsically ambiguous in this API, including possible Glock burst ordering. Live event ordering, native cvar behavior, buy-menu behavior and cross-plugin economy conflicts still need gameplay QA. No server was started to test these claims.

The pure test executable is tests/Debug.Tests.csproj and produces Debug.Tests.dll under bin/Release/net10.0. It links DebugCore.cs directly, uses no external packages and does not execute native server APIs. It covers shot correlation, penetration and stale-event rejection, reset behavior, validation, rate limits, override baseline policy, failed first-point pairing, flushed JSONL reopen/recovery and unavailable-storage handling. Both projects compile against the pinned builder image with warnings treated as errors.

EveryoneIsAdmin defaults to false. Enable it only on the isolated LAN test server to temporarily grant authenticated human players @css/root. Existing root admins are not changed. Grants owned by Debug are removed on disconnect, config reload or unload and never written to admins.json. CounterStrikeSharp supplies permissions, not general admin commands.


## Private native round-banner previews

Chat commands `!testwin`, `!testlose`, and `!testdraw` require an enabled Debug plugin and a human on T or CT. Each sends a synthetic `round_end` followed by `cs_win_panel_round` directly to the invoking player, using `FireEventToClient`. Win uses their current native team; loss uses the opposite team; draw uses winner 0/reason 10. Both manually created events are freed after sending. Three-second per-player cooldown.

These commands do not broadcast events, end the real round, change scores, change teams, or write game rules. Client rendering is experimental until checked in game. Test all three while another player watches, verify only the invoker sees the banner and the real timer, scores and movement continue. Reconnect if a client's cosmetic panel gets stuck. The server may replicate real round-end state over the fake preview; no shared state is changed to force the UI.

API references: https://docs.cssharp.dev/api/CounterStrikeSharp.API.Core.EventRoundEnd.html and https://docs.cssharp.dev/api/CounterStrikeSharp.API.Modules.Events.GameEvent.html .

Native panel previews set cs_win_panel_round.final_event to the same RoundEndReason as round_end (8 CT, 9 T, 10 draw). It is not a match-final boolean; Unknown=0 can produce an empty panel. No replicated CCSGameRules fields are changed. Client rendering still requires in-game acceptance.

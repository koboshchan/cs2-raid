DeltaOps 1.3.2 integration review

Build acceptance is not gameplay acceptance. The unchanged source compiled twice against CSS 1.0.379 and SDK 10.0.403 with zero compiler warnings/errors and identical DLL/deps/PDB hashes. No CS2 server was started, no plugin methods were run, and no deployment was made. The SDK emits a workload-verification informational notice; it does not affect the zero-warning/error compiler summary. Upstream suppresses CS0618 around its old native damage call; zero build warnings does not remove that compatibility risk.

This is an operator-ability plugin, not an extraction plugin. It contains six operators with independent V/X abilities, passives, selection menus and round-driven cooldown handling. RaidPlugin remains a separate assembly with no integration bridge.

The seven-player FFA mode cannot use the current TeamNum friend/enemy policy unchanged. DeltaOpsPlugin.cs lines 376, 399 and 460 gate kill healing, damage marks and flash marks by unequal teams. GetEnemies at 3118-3124 only treats the other T/CT team as hostile. Stinger healing at 1414-1424 and scan sharing at 2455-2465 treat all matching-team players as allies. Luna targeting/DoT at 1594 and 1641, and mine checks at 1959 and 1992 use the same assumption. Setting mp_teammates_are_enemies does not change these C# comparisons. A raid-specific per-player alliance policy must replace them before FFA acceptance.

Free utility can bypass a loot/economy system. Hackclaw, Shepherd and Vyron grant native flashbang/HE items at 1810, 1830 and 1851 through GiveNamedItemToHand at 1872-1890. Luna also receives a flashbang in ApplyPassive at 2583. Cooldowns permit repeated grants, and round resets refresh ability state. The README claims a grenade carry-limit change, but this source has no Server.ExecuteCommand/cvar setter implementing that claim. Do not assume that limit is configured. Granted-item origin must be tracked and fenced from sale, persistent stash, loot duplication and death/drop transfers, or disabled entirely until that policy exists.

ApplyPassive at 2562-2578 resets health, maximum health, speed and optionally armor; reset paths also rewrite health/speed. These can conflict with raid damage/inventory persistence. State is in-memory, keyed by SteamID for humans; it survives reconnect within a process but is cleared on match/map reset or unload. It does not provide durable stash, corpse or extraction receipts.

There are no map entity, lever, extraction zone, keycard, shop, SSG debit/credit or settlement hooks. The plugin is map-independent in source, not proof of map compatibility. Engine damage/death semantics still require an adapter so ability kills follow the raid's corpse and forfeiture rules.

Native code interaction needs installed-engine QA. DealDamage at 2781-2850 allocates raw schema-sized buffers, writes an attacker structure at a hardcoded 0x88 offset and invokes CBaseEntity_TakeDamageOldFunc with an obsolete-warning suppression. Grenade/smoke spawning, control movement and entity handles are also engine-version-sensitive. Outline code at 2871-2880 sets entity glow; do not assume the effect is private to intended teammates without two-client testing.

Server test/reset/assignment commands reject non-null player callers and are console-only, not a separate player-admin permission system. Protect RCON and backend credentials. AutoBindSkillKeys sends fixed V/X bind commands on connect/spawn/selection and may override players' choices; disable it if unwanted. No HTTP client, external process launcher or explicit filesystem access was found in the plugin source; CSS itself manages plugin configuration and logging.

Do not load both plugins together until targeting, granted-item ownership, spawn/reset behavior and map hooks have explicit designs and engine tests. The requested server target installs both assemblies, but has not been built or run. That architecture choice does not clear any integration risks above.
